# DormMate 宿舍温湿度监测系统
> 仓库：nova-dormmate-final-2026
> 已完成模块：M1~M5 + A1~A4事件处置闭环 + B3/B4 + C1/C2机器学习辅助判定

## 项目简介
DormMate 是面向宿舍场景的多节点温湿度监测演示系统。系统支持离线读取CSV文件完成数据分析与绘图；基于MQTT协议接收 dorm-a、dorm-b、dorm-c 三个宿舍节点实时JSON温湿度报文，在网页看板和3D宿舍页面可视化展示环境状态。系统自动识别环境异常、计算异常优先级，支持下发设备控制指令；持续接收报文自动判定处置效果，全部异常与操作记录写入日志，自动生成带完整事件时间线的复盘网页报告。项目配套单元测试与端到端测试。

## 环境判定规则
温湿度独立判定，同一宿舍可同时存在多个状态标签：
- 温度＜18℃ → 偏冷
- 温度≥30℃ → 偏热
- 湿度≥75% → 偏湿
- 其余情况 → 正常

## 功能总览
1. **M1**：读取CSV温湿度数据，数据校验，判定环境状态
2. **M2**：数据统计分析，生成温湿度趋势图与网页报告
3. **M3**：网页摄像头抓拍、语音识别与语音播报，支持语音指令交互
4. **M4**：采集的温湿度数据持久化存储至CSV文件
5. **M5**：Mosquitto搭建MQTT实时通信服务，MQTTX模拟宿舍节点发送报文；完成错误Topic、非法JSON报文、Broker停机三类通信故障模拟测试
6. **A1~A4事件处置闭环**：自动计算异常宿舍优先级；远程控制风扇、灯光、除湿机及学习/睡眠/离寝场景模式；接收新报文自动判断处置结果；全流程事件写入日志，生成事件复盘报告
7. **B3今日摘要**：读取事件日志中最新一天的数据，自动生成一段人话摘要（哪个宿舍出了问题、做了什么处置、结果如何），渲染在 report.html 最前面；文案全部按数据现算，换一份事件日志重新运行就整段重写
8. **B4信息分工**：同一件事不在四个页面各说一遍，而是按「这一页的人此刻要做什么」拆开——看板横幅只说「哪个宿舍、处置到哪一步、正在往哪走」（趋势跟着实际数据变，组合异常两维都报），3D 只说哪个空间需要我管、现在什么状态，语音在异常和结论出现时主动播报一句，手机端只保留三节点实时状态，完整的开始/处置/恢复/时长交给复盘报告。详见「信息分工（B4）」
9. **C1/C2机器学习辅助判定**：C1 给三个宿舍节点各训一个IsolationForest基线，让它先认识「这间房平时什么样」（训练只用历史，待判的新样本一行都不混进去，固定`random_state=42`保证可复现）；C2 拿同一批新样本让固定规则和ML各判一次并排对照。report.html 的「机器学习对比」板块**只放三张表**：各宿舍 ML 判定「接近平时」的基准（每间房自己的温湿度均值 ± 标准差，判定就是拿读数跟它比）、待判样本对照（模拟数据）、实时报文对照（app.py 随 MQTT 记下的最新 12 条实测读数，MQTTX 里新发一条、重跑报告就能看到）。两边结论不一致的格子标红；逐条「差了几个标准差」的解释只在终端输出里（`python analysis/ml_anomaly.py`），报告不重复一遍
10. **C3/C4把ML结果放回系统**：C3 让判定结果不只停在终端——`analysis.py` 跑完会把每间房的判定写成 `dashboard/ml_verdicts.json`，看板「三宿舍总览」表多出一列**ML 辅助判断**，和「异常类型」并排：左格是固定阈值判的，右格是这间房自己的历史判的，同一读数两边不一致时一眼可见（`Python 生成结果文件、页面读取展示`的轻量做法，没有为此新建后端或模型服务）；换一份历史 CSV 就能重跑（`--ml-history-dir`），判定跟着新历史变。C4 是主动给 ML 找难看：报告里「ML 判断不太理想的例子」板块每次现跑两个实验——历史砍到 5 条、历史掺入 20 条偏高读数——每个例子只写「哪条读数、判成了什么、分数多少」加一句原因，不展开分析；没出现就照实写「本次实验未出现」

## 信息分工（B4）

同一个异常从发生到收尾，会在五个地方露面。每处只回答一个问题，其余细节交给别处，**同一段文字不在两个页面重复出现**。

| 表达位置 | 信息任务 | 实际长什么样 | 为什么放在这里 |
|---|---|---|---|
| Dashboard 横幅 | 哪个宿舍、处置到哪一步、正在往哪走 | `dorm-b \| 处理中 \| 温度正在上升且湿度正在下降` | 看板是处置台，盯着最上面一行就能决定下一步按哪个按钮；异常类型/次数/已持续时长不再复述，它们在**同一页**的总览表里逐行都有，横幅再写一遍等于把最显眼的一行让给细节 |
| 3D 页面横幅 | 哪个空间需要我管、它现在什么状态 | `dorm-b 需要关注` / `dorm-b 处置中` / `dorm-b 已恢复` | 3D 是空间可视化，人看的是房间不是表格；状态词跟着处置进度变，但异常类型/次数/趋势仍不在这页 —— 点横幅带 `?node=` 跳回看板看详情，需要「为什么/怎么办」就不该在这儿找 |
| 语音提醒（自动播报） | 出事了主动喊一声，一次一个结论 | 开场「当前有 3 处需要关注：dorm-a 高温、dorm-b 高温、dorm-c 低温偏湿。」；之后「dorm-c，已恢复，温度正在上升且湿度正在下降。」 | 语音是听的，长文本播不完也记不住；它盯的是看板存下的快照，进页面先报一次当前状态（不然三间房都在异常、页面却全程静音，用户只会当这功能没生效），**之后新的异常段或新的处置结论一出现就播报**，不用等人来问（想问也可以说「朗读提醒」）。一页一句、说完就完 |
| 小程序状态卡 | 三间房现在怎么样 | 三行：`dorm-b  33.2 °C / 58 %  偏热` | 手机窄屏、碎片时间，只要「现在」；异常类型、持续时长、处置到哪一步都不搬过来——那是看板和复盘的事。数据由 app.py 订阅 MQTT 后直接存下，不经过看板 |
| 复盘报告 report.html | 完整时间线：开始、处置、恢复、持续多久 | 事件表 + 今日摘要 | 复盘是事后慢读，信息量最大，配最完整的形式 |

趋势那一段（`温度正在上升且湿度正在下降`）不是固定文案，它比的是**上一条报文 → 这一条报文**的实际变化，同一间宿舍在不同时刻说不同的话：高温处置生效说「温度正在下降」，处置没见效说「温度正在上升」，低温偏湿处置生效说「温度正在上升且湿度正在下降」。

规则在共享内核 `a1/priority.js` 的 `trendText()` 里：

- **看哪几维跟异常类型走**：高温/低温只看温度，高湿只看湿度，高温偏湿/低温偏湿两维都看。组合异常必须两维都报——只报温度那半，除湿机干了半天活在横幅上就一个字都看不到。
- **阈值滤噪声**：温度 0.5 ℃、湿度 2 % 以内算「基本平稳」，不硬报方向；两维都平稳时并成一句「温湿度基本平稳」。
- **没有可比的上一条就整段省掉**：宁可不说，也不编一句「正在上升」。

##   已知限制
1. M1~M5、A1~A4模块已完成，其余预留模块暂未开发；
​2. 离线分析仅支持本地CSV文件；
​3. 语音识别依赖浏览器Web Speech API，仅localhost环境可用；
​4. 同一时间仅开启单个Dashboard页面，多页面同时操作会产生重复事件日志；
​5. 节点停止上报数据时，处置状态会保持「处理中」，不会自动超时判定。
6. 今日摘要只反映事件日志：某宿舍「全天整体正常」的依据是当日没有异常事件记录，节点停报数据时同样会显示为正常。
7. 小程序「宿舍实时状态」卡的数据链是 MQTTX → Broker → app.py → 小程序：app.py 自己订阅 `dormmate/+/env`，收到报文就更新内存快照，小程序 GET 回来。它只要求「Broker 在跑」「app.py 在跑」「确实有节点发过报文」，**Dashboard 开不开都不影响这张卡**。看板的 POST `/api/nodeStatus` 走的是同一条写入路径（同一个函数），两条路进来的同一读数 5 秒内只记一次，不会重复计数。app.py 重启后快照清空（这是「当前时刻」不是历史，不落盘），等任一条 MQTT 报文到达就会重新填上。
8. C1/C2 用的是 `data/c12/` 下脚本生成的**模拟数据**（每行 `source` 列都写着「模拟」，不是真实采集记录）：历史由 `gen_c12_data.py` 按各节点的正态分布抽样生成，待判样本是手写的固定取值，两份数据分开存放、互不混入。规则与 ML 的对比结论以实际运行结果为准：出现不一致就在终端逐条解释（报告里只把那两格标红，不再重复一段文字），没出现就照实写「本次测试未出现」，不为凑结果调参。换一份历史 CSV 就能按 C1 的要求重跑（`--history-dir`），判定会跟着新历史变。
9. 「机器学习对比」板块里的**实时样本对照**用的是实测数据，和上一条那批模拟数据不是一回事：app.py 每收到一条 MQTT 报文就往 `data/c12/live_samples.csv` 追加一行（`source=实时`，同一读数 5 秒内只记一次，文件只保留最新 120 行），重新生成报告时用**同一批模型和同一条固定规则**去判它，取最新 12 条显示——所以表格里出现的一直是最近发过的报文，不会停在模拟样本上。这份数据只用于离线回看，不参与 Dashboard 的实时判定，实时链路走的仍是固定规则。`live_samples.csv` 是运行时数据，已加进 `.gitignore`；重跑 `gen_c12_data.py` 不会覆盖它（只在文件缺失时建一个空表）。
10. 看板「ML 辅助判断」列是**上一次跑分析时**的结论，不随 MQTT 报文实时变：`ml_verdicts.json` 由 `analysis.py` 生成，页面上读数在上次分析的样本里找得到就显示那条判定，找不到就沿用最新一条并标「上次分析」。要刷新这一列就重跑 `python analysis/analysis.py`。另外这一列的基线来自**模拟历史数据**，用途是演示「每间房各自设基线」这套机制，不是对真实宿舍下的结论。
11. ML 判断不一定准，这不是实现缺陷而是方法本身的边界：报告里「ML 判断不太理想的例子」板块用两个实验（历史砍到 5 条、历史掺入 20 条偏高读数）把它的短板摆出来——历史太少时判定会不稳，历史本身有问题时模型不会报警反而会把错误学成常态。所以 ML 始终和固定规则并排显示、只当补充，不单独下结论。
12. 语音提醒读的是看板存在 localStorage 里的快照，因此要求 web 页与 Dashboard 同源打开（和 3D 页读取看板状态是同一个前提），且至少打开过一次 Dashboard；两个条件都不满足时，说「朗读提醒」它会照实回答「看板数据不存在，请先打开 Dashboard 页面」，而不是沉默。语音提醒**只在页面打开时念一遍**：把当下已有的异常攒成一句「当前有 3 处需要关注：dorm-a 高温、dorm-b 高温、dorm-c 低温偏湿。」，念完就不再主动出声——之后新出现的异常段、处置结论都不念，想听就问一句「朗读提醒」。若那一刻页面还没有可念的东西（看板没开过、或谁都不异常），同样不会再开口。念的那一遍用户一下指令就作废（同一时刻只有一个喇叭，用户的话优先）。播报期间说的话会被语音识别当成回声丢掉（M3 起就有的守卫），想下指令等它念完再说一遍即可。播不出来时不会静默：状态栏会写明原因（浏览器要求先点一下页面 / 系统没有可用的中文语音 / 引擎报错），且那一句不会被算作「已念」—— 点一下页面就会立刻补播（只补一次），之后每 2.5 秒的轮询也会自动重试。
